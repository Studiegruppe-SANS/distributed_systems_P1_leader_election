# Docker / Kubernetes simulation

Each node runs the leader election code in its own container. There are two ways to run the
cluster, and both use the same image (`bully-app:latest`):

| | Docker Compose | Kubernetes (kind) |
|---|---|---|
| Use for | Fast development and the automated system test | Orchestrated deployment and the experiments in the report |
| Start time | Seconds | About 1 minute (cluster) plus about 20 s (pods) |
| Node addresses | `localhost:8080` … `localhost:808N` | `bully-N.bully:8080` inside the cluster (headless service) |
| Kill a node | `curl -X POST localhost:8084/crash` | `python3 experiment.py crash-middle` etc. |

All commands below are run from the **repo root** unless stated otherwise.

## Setup

One-time setup on macOS. Every group member needs this to run the nodes in containers.

### 1. Install the tools

| Tool | Purpose | Install |
|------|---------|---------|
| Docker Desktop (or OrbStack/Colima) | Builds and runs the containers | https://www.docker.com/products/docker-desktop or `brew install --cask docker` |
| kubectl | Talks to the Kubernetes cluster | `brew install kubectl` |
| kind | Runs a local Kubernetes cluster inside Docker | `brew install kind` |
| Python packages | System test and plots (on your Mac, not in the image) | `pip install -r requirements-dev.txt` |

Start Docker Desktop, then check that everything is installed:

```bash
docker version
kubectl version --client
kind version
```

### 2. Create the local cluster

```bash
make kind-up        # kind create cluster --name bully --config docker/k8s/kind-cluster.yaml
                    # + kubectl apply -f docker/k8s/headless-service.yaml
kubectl cluster-info --context kind-bully   # should print the control plane address
```

The cluster has 1 control-plane node and 2 worker nodes (`docker/k8s/kind-cluster.yaml`),
so the pods are spread over several "machines".

### 3. Build the image and load it into the cluster

The StatefulSet uses `imagePullPolicy: Never`, so Kubernetes will not pull the image from
a registry. You have to load your local image into kind yourself, and do it again
**after every code change**.

```bash
make kind-load      # docker build -t bully-app:latest docker/ && kind load docker-image bully-app:latest --name bully
```

### 4. Deploy the nodes

```bash
make deploy ALGO=classic N=5     # or ALGO=improved
kubectl get pods                 # bully-0 ... bully-4 should be Running and READY 1/1
make status                      # all nodes should agree on leader 4
```

`deploy` deletes the old pods and starts new ones. It does **not** edit
`k8s/statefulset.yaml` on disk; it sends a modified copy to Kubernetes.

### 5. Clean up

```bash
make kind-down      # kind delete cluster --name bully
```

## Running with Docker Compose (no Kubernetes)

```bash
make compose-up ALGO=improved N=5     # generates docker/compose.yaml and starts N nodes
curl localhost:8084/status            # node 4's state, leader and message counts
curl -X POST localhost:8084/crash     # node 4 "dies"
curl localhost:8080/status            # after about 10 s node 0 points to leader 3
curl -X POST localhost:8084/recover   # node 4 comes back and bullies its way to leader
cd docker && docker compose logs -f   # follow all nodes' logs
make compose-down
```

`docker/compose.yaml` is generated by `docker/gen_compose.py`. Edit the generator, not the file.

## Experiments (Kubernetes)

`docker/experiment.py` drives the pods through `kubectl` and adds up the message counts from
every pod's `/status`.

| Scenario | What happens | Expected leader |
|---|---|---|
| `startup` | All pods are started from scratch | N−1 |
| `failover` | The leader pod is deleted; all nodes detect it via heartbeat timeout | N−2 |
| `worst` | The leader is deleted and **only node 0** starts the election (worst case) | N−2 |
| `crash-middle` | A random non-leader crashes; there should be no election | N−1 |
| `crash-two` | The two highest nodes crash at the same time | N−3 |
| `recover-leader` | The leader crashes, a new one is elected, then the old one comes back | N−1 |

```bash
python3 docker/experiment.py worst                                  # one run, table in the terminal
python3 docker/experiment.py crash-two --runs 5 --out results/crash-two.csv
make experiments                          # everything: scenarios x both algorithms x N=5,10,15,20 -> results/sweep-*.csv
make experiments RUNS=3 NS="5 10"         # repeat each scenario 3 times, only N=5 and 10
make plots                                 # graphs + summary table -> results/plots/
```

Each scenario continues as soon as all nodes agree on a leader, so a single run takes roughly
15–40 s (crash scenarios have to wait for the 5 s heartbeat timeout). By default each scenario runs once.
Only run one experiment at a time: two runs on the same cluster crash and redeploy each other's nodes.

**What is measured** (one CSV row per run):

- `ELECTION`, `OK`, `COORDINATOR`, `total`: election messages sent by all nodes since the
  scenario started. Heartbeats are counted separately and are not included.
- `leader`, `agreement`, `correct`: whether all live nodes agree, and whether they agree on the expected node.
- `election_time_s`: time from the first node starting an election until the last node learned
  the new leader. The time it takes to *detect* the crash (heartbeat timeout) is not included.
  The runner (`app.py`) records it by watching the node after every call, so the algorithm code
  is not touched.
- `expected_total`: the theoretical message count, where it is known (`worst`: classic n(n−1), improved 3n−3).

## Unit tests

```bash
python3 -m pytest testing/test_bully_node.py -v    # under 1 second, no Docker needed
```

`testing/test_bully_node.py` tests the algorithm classes directly, with a fake network and a
fake clock. It checks that each node sends the right messages, and that a 5-node worst case
gives the right leader with n(n−1) messages (classic) and 3n−3 messages (improved).

## System test

```bash
make test           # = python3 -m pytest testing/ -v   (unit tests + system test, requires Docker)
```

For **each** algorithm, `testing/test_system.py` starts a 5-node Compose cluster and checks that:

1. after startup, every node agrees on node 4,
2. when the leader crashes, node 3 is elected, and node 4 takes over again when it recovers,
3. when the two highest nodes crash, node 2 is elected,
4. when a non-leader crashes, no election is started,
5. the worst case uses exactly n(n−1) messages (classic) or 3n−3 messages (improved).

## HTTP endpoints (each node, port 8080)

| Endpoint | Purpose |
|---|---|
| `POST /message` | Messages between the nodes (used by the algorithm) |
| `GET /status` | State, leader, message counts, timestamps, `crashed` |
| `POST /stats/reset` | Reset message counts before an experiment |
| `POST /election` | Force this node to start an election |
| `POST /crash` | The node behaves as dead: ignores messages, sends nothing. `/status` still answers. |
| `POST /recover` | The node restarts with fresh state and starts an election (Garcia-Molina's recovery case) |

## Troubleshooting

- **`ErrImageNeverPull`**: you forgot `make kind-load` (step 3).
- **The pods run old code**: run `make kind-load` and then `make deploy` again.
- **The nodes don't agree on a leader**: wait about 15 s (startup delay plus the election), then run `make status` again.
- **See a node's log**: `kubectl logs bully-3 -f` (Kubernetes) or `cd docker && docker compose logs -f bully-3` (Compose).
- **`port is already allocated`** (Compose): something else is using 8080–808N. Run `make compose-down`, or stop the other program.
- **An experiment was interrupted while a node was crashed**: the next scenario revives it automatically. You can also run `curl -X POST .../recover` yourself, or `make deploy`.
